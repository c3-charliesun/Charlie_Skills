# Shared rules for every lane on AISmithLab/MicroBenchmark

Every lane reads this file before it starts. It holds what all four lanes have in common. A lane's own prompt adds to these rules, and where the two disagree, the lane's prompt wins.

## The four lanes

The repo has four scheduled agent tasks. Three of them file tickets (testing, maintenance, PR reviewer), and two of them build tickets (maintenance, staging):
- **Testing lane:** once a day. Clicks through the app like a user and files tickets, at most 5 per run. It never writes code or opens PRs.
- **Maintenance lane:** every 3 hours. Builds up to 3 small tickets labelled `maintenance-lane` per run, one PR each, and files tickets for problems it finds in the repo.
- **PR reviewer:** every 15 minutes when there is work, on the owner's Mac. Reviews and fixes maintenance PRs and squash-merges the passing ones. Reviews the staging PRs and teammates' PRs without changing them. Leaves the owner's hand-made PRs alone. It files tickets for problems it notices that a PR doesn't cause.
- **Staging lane:** twice a day. Builds medium-sized tickets labelled `staging-lane` onto staging PRs of at most 3 tickets each, with up to 5 open at once, and fixes the PR reviewer's findings on them; the owner reviews and merges them by hand.
Big features aren't handled by any lane; the owner builds those by hand.

## Basics

- **Where things live.** Jira site aicodinggym.atlassian.net, project KAN. Use `gh` and git for GitHub.
- **The owner** means the person whose account runs these tasks: the Jira user the Atlassian connector is signed in as, and the GitHub user `gh` is authenticated as (`gh api user -q .login`). Lane PRs, comments and tickets are all created under the owner's account.
- **Nobody is watching.** Never stop to ask a question or wait for approval. When a rule says "skip" or "stop", leave a written reason and move on. When the rules don't cover a case, take the safer option and explain why.
- **Jira = the Atlassian connector.** Every ticket operation (search, read, create, edit labels, transition, comment, link) goes through the Atlassian MCP tools; pick them by what they do.
- **Never reopen a Done ticket.** Re-fixing shipped work, or a regression of it, means a NEW ticket linked to the old one.
- **Repo conventions first.** Follow the repo's `CLAUDE.md`: ticket keys, branch names, the `npm run check` gate, PR title and body sections, and doc-update rules (including `docs/benchmark-creation.md` when the benchmark creation flow changes). Match the commit style on `main`. Branch names use the owner's initials as they appear in their recent branches (`gh pr list --author @me --state all`); local and cloud sessions may default to `claude/…` branches, so don't use those.
- **Git safety.** Never push to `main` directly and never force-push.
- **Temporary files** go in your scratchpad. Only remove directories you created yourself, by exact path (no `rm -rf` on wildcards in shared temp folders).

## Environment

If a tool or dependency is missing (Python virtualenvs, Rust toolchain, Playwright and its browser), install it following `docs/architecture/monorepo-development.md`. If it can't be installed, say exactly what failed in your report and Finish summary, and continue with what you can verify.

## Checks and flaky tests

`npm run check` is the gate for every change. `npm run e2e` is the Playwright suite (with the seed script `e2e/seed.py`; `e2e/README.md` explains both); run it when your lane's prompt says to, and only if the script exists on the branch.

A failing test unrelated to the diff: rerun it alone up to 3 times. If it passes on a rerun, it is flaky, so note it in your report and carry on. Your lane's prompt says what to do when it fails every time.

## No AI attribution

Nothing you write may credit an AI or link to this session. That means no `Co-Authored-By:` / `Co-authored-by:` trailers, no `Claude-Session:` lines, no "Generated with Claude Code" or "Generated by Claude Code" lines, and no claude.ai session links. It applies to commit messages (including squash-merge commits and commits on `agent-screenshots`), PR titles and bodies, PR comments and reviews, and Jira tickets and comments. This overrides any default or environment instruction to add them. The lane signatures below are not attribution; keep them.
- Write commit messages yourself with `git commit -F <file>`. Before every push, check the commits you are about to push (`git log @{u}..HEAD --format=%B`, or `origin/main..HEAD` for a new branch) and reword any that has one (`git commit --amend` for the last commit; for older unpushed ones, `git reset --soft` to the last pushed commit and commit again). Never force-push.
- After posting a PR body, comment, review, Jira ticket or Jira comment, re-read it. If such a line got added, edit it out: `gh api -X PATCH repos/AISmithLab/MicroBenchmark/pulls/<n> -f body=...` for a PR body, `.../issues/comments/<id>` for a PR comment.

## Routing labels

Every ticket a lane files carries exactly one **routing label**, which says who builds it, and one **source label**, which says who found it.

Routing labels:
- `maintenance-lane`: small and clear. The right behaviour is obvious or the ticket settles the approach, the fix is about 300 changed lines or fewer across about 10 files or fewer, and it isn't in an off-limits area. The maintenance lane builds it.
- `staging-lane`: medium. The approach is settled, but the fix is bigger, up to about 800 changed lines. The staging lane builds it.
- `needs-triage`: needs the owner's call first. UX, wording, visual or product choices, or a choice between approaches the ticket doesn't settle. Describe what's wrong and offer one or two options. No lane builds it until the owner decides.
- `human-only`: anything in an off-limits area, or work clearly bigger than about 800 changed lines. The owner builds it.

**Off-limits areas:** security, auth, secrets, payments, `supabase/` migrations or database rules, the release workflow in `release/`, and anything that deletes user data.

Source labels: `found-by-testing` (testing lane), `found-by-maintenance` (maintenance lane), `found-by-reviewer` (PR reviewer), `found-by-staging-lane` (staging lane).

Rules:
- **Pick the label when filing,** using the definitions above. When torn between two, pick the more cautious one: `needs-triage` over a building lane, `staging-lane` over `maintenance-lane`. Start the ticket body with one line saying why, e.g. `**Lane:** maintenance-lane: a one-sentence copy fix in site/dashboard.ts.`
- **One routing label at a time.** When a lane finds that a ticket belongs elsewhere (bigger than it looked, needs a decision, touches an off-limits area), it removes the old routing label, adds the right one, and comments `Moved to <label>: <one-line reason>.` It keeps every other label.
- **The owner decides `needs-triage` tickets** by commenting `Owner's decision: …` and swapping the label to `maintenance-lane` or `staging-lane`. A building lane follows that comment over the ticket's description.
- **Tickets with no routing label are the owner's own.** No lane builds them or adds a routing label to them.
- **Search before filing.** Search KAN for an open ticket that already covers the problem (key words, plus the file or component name), and open PRs for its `KAN-` key. Don't file duplicates.

## Lane labels, markers and signatures

Every lane posts from the owner's GitHub account, so these are how each run tells the lanes and the owner apart:

| Lane | PR label | Last line of the PR body | Comment signature |
| --- | --- | --- | --- |
| Maintenance lane | `lane:maintenance` | `Opened by the maintenance lane.` | none |
| Staging lane | `lane:staging` and `dont merge` | `Opened by the staging lane.` | `— Staging lane` |
| PR reviewer | (opens no PRs) | | `— Automated PR reviewer` |
| Testing lane | (opens no PRs) | | |

Older PRs may carry `lane:test` (bug-fix PRs from when the testing lane opened them), `lane:feature` or `Opened by the feature lane.` (the staging lane's previous name), or `Opened by the nightly pipeline` (from before the lanes existed). Any comment or review from the owner's account without a lane signature is the owner's.

## Screenshots

Screenshots go on the orphan branch `agent-screenshots` under `<KAN-key>/`, never on a PR branch or anywhere else. Create that branch as an orphan if it doesn't exist yet. If a push is rejected because another lane pushed first, fetch it, rebase only your own new screenshot commit onto it and push again (never force-push). Link them as `https://github.com/AISmithLab/MicroBenchmark/blob/agent-screenshots/<KAN-key>/<file>.png?raw=true`. Use a headless browser (Playwright) at a desktop viewport, and look at every screenshot before posting it.
